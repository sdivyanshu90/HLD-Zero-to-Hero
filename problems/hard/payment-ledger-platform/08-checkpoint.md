# Step 8 — Checkpoint & Interview Q&A

**Q1: What is double-entry bookkeeping and why is it used?**
> Every financial transaction records two equal and opposite entries (debit + credit) that sum to zero. This is an invariant: at any point, sum of all debits = sum of all credits. It prevents money from being created or lost. It enables easy reconciliation: if the sum doesn't equal zero, there's a bug. Used by all serious financial systems since 14th century.

**Q2: How do you make payments idempotent?**
> Each payment request includes a unique idempotency_key (e.g., UUID v4 generated by client). Server does `INSERT INTO payment_requests ... ON CONFLICT (idempotency_key) DO NOTHING`. If key already exists, return the result of the first request. This allows safe retries on network failure — the payment happens exactly once even if the request is sent multiple times.

**Q3: Why use SERIALIZABLE isolation for the transfer transaction?**
> The balance check and debit must be atomic. With READ COMMITTED isolation, two concurrent transfers from Alice's $100 account can both read $100, both pass the balance check, and both succeed — leaving Alice at -$100. SERIALIZABLE isolation prevents this phantom read scenario by detecting conflicting concurrent transactions and aborting one.

**Q4: How do you query the current balance efficiently?**
> Two approaches: (1) Materialized balance — maintain a running balance_after column on each ledger entry. Latest balance = most recent entry's balance_after (one row read). Risk: must update atomically with the insert. (2) Separate accounts table — UPDATE accounts SET balance = balance + delta. Either way, use Redis to cache hot account balances with a short TTL (5 seconds).

**Q5: How do you handle a payment that's stuck in "pending" state?**
> A saga-style compensating transaction: if payment is pending for > 30 seconds (timeout), the payment service initiates a reversal. If the original COMMIT happened (entry exists in DB), reversal is a new transfer in the opposite direction. If COMMIT didn't happen (no entry), mark idempotency_key as failed. Outbox pattern: write to Kafka after DB commit to trigger settlement events reliably.
