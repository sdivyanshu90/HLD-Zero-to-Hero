# Reliability Patterns: At-Least-Once, At-Most-Once, Exactly-Once

## The Delivery Semantics Spectrum

```
At-most-once:
  Message may be lost but never processed twice
  Producer sends → may never be received
  Use when: loss is OK, duplicates are worse (metrics fire-and-forget)

At-least-once:
  Message processed one or more times, never lost
  On failure: retry → may be processed multiple times
  Use when: missing data is unacceptable, processing is idempotent
  (most common choice in practice)

Exactly-once:
  Message processed exactly one time, never lost, never duplicated
  Very hard to implement correctly
  Use when: financial transactions, state changes that can't be undone
  (requires transactional semantics, idempotency keys, or distributed transactions)
```

## At-Least-Once: The Practical Default

```
How it works (Kafka example):
  1. Producer writes message to Kafka (message persisted on broker)
  2. Consumer reads message, processes it
  3. Consumer crashes before committing offset
  4. Consumer restarts, reads from last committed offset
  5. Message is reprocessed → processed TWICE

  This is AT-LEAST-ONCE: guaranteed delivery, possible duplicates

Making at-least-once safe: IDEMPOTENCY
  Idempotent operation: processing N times = same result as processing once
  
  Idempotent examples:
    SET user.name = "Alice"     → same result no matter how many times
    INSERT OR IGNORE INTO ...   → duplicate inserts are no-ops
    PUT /resource/123           → idempotent HTTP method
    
  Non-idempotent examples:
    INCREMENT counter           → each retry adds 1 more!
    CHARGE CREDIT CARD $100     → each retry charges $100 again!
    SEND EMAIL                  → each retry sends another email!

  Making non-idempotent operations idempotent:
    Use an idempotency key:
      payment_id = UUID (generated by client, same on retry)
      INSERT INTO payments (payment_id, amount, ...)
        ON CONFLICT (payment_id) DO NOTHING
      → First insert: creates payment
      → Retry: conflicts on payment_id → no-op
      → Exactly one payment created regardless of retries!
```

## Kafka Idempotent Producer

```
Without idempotent producer:
  Producer sends message to Kafka broker
  Broker writes message, but ACK is lost in transit
  Producer times out → RETRIES the message
  → Message is now duplicated in Kafka log!

With idempotent producer (enable.idempotence=true):
  Producer assigns each message a Sequence Number per partition
  Broker tracks last seen sequence number per producer-partition
  On retry: broker sees same sequence number → deduplicates → one write only

  Configuration:
    enable.idempotence=true  → idempotent producer
    acks=all                 → all replicas must ACK (default with idempotence)
    max.in.flight.requests.per.connection=5  → retries maintain ordering

  This gives EXACTLY-ONCE at the producer level (no duplicates in Kafka)
  But not end-to-end: consumer still needs to handle idempotency
```

## Kafka Transactions: End-to-End Exactly-Once

```
Use case: read from topic A, process, write to topic B
  Without transactions:
    Read from A → process → write to B
    Crash after writing to B but before committing offset in A
    → Restart: reprocess same message → write to B again → DUPLICATE in B!

With Kafka transactions:
  producer.initTransactions()
  
  loop:
    ConsumerRecords records = consumer.poll()
    producer.beginTransaction()
    
    for record in records:
        processedResult = process(record)
        producer.send("topicB", processedResult)
    
    # Commit offset AND output atomically
    producer.sendOffsetsToTransaction(offsets, consumerGroupId)
    producer.commitTransaction()  ← atomic commit of offsets + output
  
  If crash during transaction → transaction aborted → consumer replays from last offset
  → Exactly-once semantics!

Overhead:
  Transactions add latency (~10ms coordination overhead)
  Suitable for: billing, ledgers, critical event processing
  Not needed for: analytics, logging, non-critical processing
```

## Saga Pattern for Distributed Transactions

When a transaction spans multiple services (not just Kafka → Kafka):

```
Order processing saga:
  Step 1: Reserve inventory (Inventory Service)
  Step 2: Charge credit card (Payment Service)
  Step 3: Create shipping label (Shipping Service)
  Step 4: Send confirmation email (Notification Service)

Choreography-based Saga (event-driven):
  OrderCreated event ──▶ Inventory Service
    → publishes InventoryReserved event
  InventoryReserved event ──▶ Payment Service
    → publishes PaymentCharged event
  PaymentCharged event ──▶ Shipping Service
    → publishes ShipmentCreated event
  ShipmentCreated event ──▶ Notification Service

Compensation on failure:
  If Payment fails:
    Payment Service publishes PaymentFailed event
    Inventory Service listens → publishes InventoryReleased (compensation)
    Order Service listens → marks order CANCELLED

  Each step has a compensating transaction that undoes it
  Saga is eventually consistent (not ACID)

Orchestration-based Saga:
  Central Saga Orchestrator drives the workflow:
    Orchestrator calls Inventory → Inventory responds OK
    Orchestrator calls Payment → Payment responds OK
    Orchestrator calls Shipping → Shipping fails
    Orchestrator calls Inventory compensation (release reserved items)
    Orchestrator returns error to client

  Easier to reason about (centralized logic)
  Risk: orchestrator is a single point of failure
```

## Retry Patterns and Exponential Backoff

```
Naive retry (bad):
  for i in range(3):
      try:
          result = process(message)
          break
      except:
          continue  ← immediate retry → thundering herd on service failures

Exponential backoff with jitter (good):
  delay = base_delay * (2 ** attempt) + random(0, jitter)
  
  Attempt 0: delay = 0
  Attempt 1: delay = 1s  + random(0, 0.5s) = 1.3s
  Attempt 2: delay = 2s  + random(0, 1s)   = 2.7s
  Attempt 3: delay = 4s  + random(0, 2s)   = 5.2s
  Attempt 4: delay = 8s  + random(0, 4s)   = 11.4s
  Max delay cap: 60 seconds (don't grow forever)
  Max attempts: 5-10 (then send to DLQ)
  
  Jitter prevents synchronized retries from all consumers
  (without jitter: all retry at exactly t=2s → spike → more failures)

AWS SDK: automatic exponential backoff on all service calls
Kafka consumer: configurable retry.backoff.ms
Spring Retry: @Retryable(maxAttempts=3, backoff=@Backoff(delay=1000, multiplier=2))
```

## Interview Quick Answers

- **What is the difference between at-least-once and exactly-once?** — At-least-once: messages are never lost but may be processed multiple times on failure/retry. Safe with idempotent operations. Exactly-once: each message processed exactly once. Requires idempotency keys, Kafka transactions, or distributed coordination. Much harder to implement.
- **How do you implement exactly-once with Kafka transactions?** — Use Kafka producer transactions: wrap `consumer.poll()`, processing, `producer.send()`, and offset commit in a `beginTransaction()/commitTransaction()` block. The offset commit and output writes are atomically committed. On crash, the transaction is rolled back and the consumer replays from the last committed offset.
- **What is the Saga pattern?** — A sequence of local transactions where each step publishes an event/command that triggers the next step. If a step fails, compensating transactions undo the previous steps. Achieves distributed consistency without distributed ACID transactions. Used for multi-service workflows (order processing, booking systems).
